Fleet Management & Live Bus Tracking
Engineering Specification v1.0 (Android and iOS)
Developer blueprint for the MVP. Companion to SRS v1.1. Hosting and cost are intentionally excluded.
This specification tells the team what to build and how, so that location data flows from Android and iOS phones to the dashboard map in under 3 seconds, and every MVP requirement in SRS v1.1 maps to a component, an API and a test.

1.3 Engineering rules
TypeScript strict mode everywhere; no any without a comment explaining why.
All timestamps are UTC timestamptz; the UI formats in IST. IDs are UUIDs generated by the application (time-ordered UUIDv7 preferred).
Every business row carries org_id; every query takes orgId explicitly. No exceptions.
Input is validated with Zod at every boundary (HTTP, WebSocket, queue payloads, environment).
Errors use RFC 9457 application/problem+json with a stable code field.
Every state-changing endpoint writes an audit entry in the same transaction.
Migrations are forward-only SQL files. Secrets never appear in code, logs or client bundles.
Logs are structured (pino) and carry requestId, orgId, and busId or tripId where relevant.

2. Architecture
2.1 Runtime view of the live data path
The driver starts a trip in the app. The app creates a local trip record, begins background location updates and writes every point to a local SQLite queue.
An uploader sends queued points in batches (up to 200) to POST /v1/ingest/locations.
The API authenticates the installation, validates each point, inserts history idempotently, and updates the bus's latest-location row only if the point is newer, all in one transaction.
If the latest row changed, the API emits a bus.updated event to the organization's Socket.IO room.
The dashboard applies the event to its map state and moves the marker.
Every 15 s the worker sweeps for buses that stopped reporting, sets them Stale or Offline, raises alerts and notifies the API, which emits the events.
On any dashboard reconnect, the client fetches a snapshot (GET /v1/live/buses) and then resumes events, so nothing is missed.

5. Live Data Ingestion
5.1 Request and response
POST /v1/ingest/locations, bearer token of an installation session. Limits: up to 200 points and 256 KB per request; 60 requests a minute per installation.
{  "sent_at": "2026-11-02T03:15:12.000Z",  "trip_id": "0192f0a1-7c3e-7c11-9d0a-5e2b6f4c1a10",  "points": [    { "id": "0192f0a1-8a01-7d22-8b31-1f6d2a9c0b01",      "recorded_at": "2026-11-02T03:15:10.000Z",      "lat": 18.5204, "lng": 73.8567,      "accuracy_m": 8, "speed_kmh": 32.4, "heading_deg": 90 }  ],  "health": { "battery_pct": 71, "charging": true, "network": "4g",              "permission": "always", "queue_depth": 0, "app_version": "1.0.3" }}

{  "server_time": "2026-11-02T03:15:12.240Z",  "results": [ { "id": "0192f0a1-8a01-7d22-8b31-1f6d2a9c0b01", "outcome": "accepted" } ],  "config": { "interval_moving_s": 10, "interval_still_s": 30 },  "min_app_version": "1.0.0"}
A processed batch returns 200 even when some points are rejected; the per-point outcome is accepted, duplicate or rejected (with reason). Batch-level failures use 400 (schema), 401 (no or expired token), 403 (installation revoked or trip not assigned to this driver), 413, 429 (with Retry-After) and 5xx. The app deletes only points that came back accepted, duplicate or rejected, and retries everything else.
Clock handling. The server never rewrites recorded_at. The app obtains server_time from every response (and from GET /v1/time at trip start), keeps an offset, and stamps points with corrected UTC. Rewriting on the server would make retries produce different keys.

One rule for weak fixes (accuracy above 100 m, or accuracy missing).
The app does not filter them. It records and uploads every fix with its accuracy, so the server is the only place the rule is applied.
The server stores them in history with the low_accuracy flag (bit 1 of flags).
They never update the latest location, so the map does not jump on a weak fix.
They are excluded from distance, speed, overspeed and prolonged-stop calculations, and from the newest good point used for status.
Replay shows them as dimmed points.
If only weak fixes arrive, the bus becomes Stale and then Offline. The alert records the last accuracy and battery from the health block, so a dispatcher can tell a signal problem from a dead phone.
The capture rate counts every recorded fix; the GPS availability report counts good fixes only.

'accepted' : 'duplicate'));    const newest = pickNewestGood(valid);                       // newest point with accuracy <= 100 m    const row = newest && await upsertLatest(trx, ctx, newest, batch.health);    await audit.ingestSummary(trx, ctx, results);              // counts only, not per point    return row;                                                 // undefined when nothing was newer  });  if (changed) events.emitBusUpdated(ctx.orgId, changed);       // after commit  await evaluateIngestAlerts(ctx, valid);                       // overspeed, prolonged stop  return { server_time: new Date().toISOString(), results, config: cfg(ctx), min_app_version };}
The history insert uses the real column names. The request field points[].id is the app's client_point_id; the parser renames it, and the handler uses clientPointId afterwards. The statement returns only newly inserted rows, so any point missing from the result is a duplicate.

6. Status Engine, Alerts and Trip Rules
6.1 Status
Status is computed from the age of the latest good point and the trip state, never from the last speed alone.
export function computeStatus(nowMs, last, tripActive, cfg): BusStatus {  if (!tripActive) return 'not_on_trip';  if (!last) return nowMs - tripStartMs >= cfg.firstFixGraceMs ? 'offline' : 'stale';  const ageS = (nowMs - last.recordedAtMs) / 1000;  if (ageS <= cfg.freshS)   return isStopped(last, cfg) ? 'stopped' : 'moving';  if (ageS <= cfg.offlineS) return 'stale';  return 'offline';}
Defaults: freshS 60, offlineS 300, firstFixGraceMs 120 000, moving threshold 5 km/h. To stop a bus flickering at a red light, isStopped is true only when speed has been under 5 km/h continuously for at least 30 s, tracked with slow_since.
Sweep (worker, every 15 s). One set-based query finds buses with an in-progress trip whose latest point is older than 60 s, updates status and status_since, bumps rev, and returns the changed rows. Each changed row raises or resolves the matching alert and emits bus.status through NOTIFY. A second query handles in-progress trips that have no latest row at all. The sweep is idempotent, so two overlapping runs cannot produce duplicate alerts (the unique open-alert index guarantees it).

6.3 Trip rules
States: Scheduled to In Progress to Completed; Scheduled or In Progress to Cancelled. Anything else returns 409. Delayed is a flag on the trip, not a status.
Start: the driver must be assigned to the trip, the bus and the driver must have no other in-progress trip (the partial unique indexes enforce this), and the start must fall within the planned window plus or minus 2 hours unless a manager overrides. The server records actual_start from the app's corrected timestamp.
End: the app first flushes its queue, then calls end. The server sets actual_end, queues a job that computes distance and closes any open alerts for the trip.
Force close: a manager can end a trip with a mandatory reason; closed_by is admin and the action is audited. A trip with no points for 6 hours is closed by the watchdog with closed_by set to system.
Distance: computed once at trip end from good points (accuracy 100 m or better), ignoring segments under 5 m to avoid drift:
SELECT COALESCE(SUM(d), 0)::int FROM (  SELECT ST_Distance(           ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography,           ST_SetSRID(ST_MakePoint(LAG(lng) OVER w, LAG(lat) OVER w), 4326)::geography) AS d  FROM trip_locations  WHERE trip_id = $1 AND (flags & 1) = 0           -- bit 1 = low_accuracy  WINDOW w AS (ORDER BY recorded_at)) s WHERE d >= 5;
Recurrence: a daily job turns trip_templates into concrete trips for the next 14 days; regenerating is idempotent per template and date.
Route versions: a trip stores its route_version_id, so editing a route never changes history.

7. API Specification
7.1 Conventions
Base path /v1; JSON; Authorization: Bearer <access token>; OpenAPI generated from the Zod route schemas and published in CI.
Errors are application/problem+json with type, title, status, detail and a stable code (for example trip.invalid_transition, auth.locked, ingest.batch_too_large).
Lists use cursor pagination (?limit=50&cursor=..., maximum 200) with documented filter and sort parameters.
State-changing driver endpoints require an Idempotency-Key header; a replay returns the stored response.
Role codes: SA super admin, FM fleet manager, SV supervisor (read-only), DR driver.
Every route declares its roles in code; a test walks the route table and fails if any route lacks a guard or an organization-scope check.
7.2 Authentication and sessions
Dashboard login: email and password return a 15-minute access JWT (claims sub, org, role, sid). The refresh token is an opaque 256-bit value in an HttpOnly; Secure; SameSite=Strict cookie scoped to /v1/auth; the web app keeps the access token in memory only.
Driver login: phone number, 6-digit PIN and installation_id. Tokens go to the app's secure storage; sessions last 30 days, rolling. Five failed attempts lock the account for 15 minutes. A new driver's first login forces a PIN change. An admin can revoke any installation instantly.
Refresh rotation: each refresh issues a new refresh token and invalidates the old one. Presenting an already-used token revokes the whole session family.
Storage: refresh tokens are stored as SHA-256 hashes; passwords with Argon2id; PINs with Argon2id and a throttled comparison.
Password policy: at least 10 characters; reset tokens are single-use and expire in 30 minutes; every reset and login failure is audited.

8. Real-Time Delivery to the Dashboard
8.1 Connection and rooms
The client connects with auth: { token }. The server verifies the JWT, rejects driver tokens, and joins the socket to exactly one room, org:{orgId}. Clients can never choose rooms.
Before the access token expires the client sends auth:refresh with a new token; a socket whose token expires without refresh is disconnected.
Events are versioned (v: 1) so the payloads can change without breaking old dashboards.

The API keeps a per-organization map of the latest point per bus and flushes it every 1000 ms, so 100 buses reporting every 5 s produce at most one message a second, not 20. Status and alert events are never delayed by the coalescer.
8.3 Resynchronization protocol (what makes the data trustworthy)
On connect, wait for server.hello, then call GET /live/buses. The response holds every bus and a snapshot_rev, read in one statement so it is consistent.
While the snapshot loads, buffer incoming events.
Apply the snapshot, then apply buffered and later events. For each bus, ignore any event whose rev is not greater than the stored rev.
On disconnect, show a banner after 5 s and reconnect with backoff (1 to 10 s with jitter). Every reconnect repeats step 1; the client never assumes it missed nothing.
If no event and no heartbeat arrives for 60 s, treat the connection as dead and reconnect.
The "x seconds ago" text is computed on the client from recorded_at, so it keeps counting up even when no events arrive. The status itself always comes from the server.

9.4 Tracking service
await Location.startLocationUpdatesAsync(TRACKING_TASK, {  accuracy: Location.Accuracy.High,  timeInterval: 5000,                 // Android  distanceInterval: 0,                // all updates; throttled in the callback  pausesUpdatesAutomatically: false,  // iOS  activityType: Location.ActivityType.AutomotiveNavigation, // iOS  showsBackgroundLocationIndicator: true,                   // iOS  foregroundService: {                // Android    notificationTitle: 'Trip in progress',    notificationBody: 'Sharing location with dispatch',    killServiceOnDestroy: false,  },});
The task callback does four things: read the fix with its accuracy (no accuracy filtering on the phone; the server applies the weak-fix rule in section 5.2), apply the throttle, write the point to SQLite, and return. The throttle gives both platforms the same cadence: store a point when time since the last stored point is at least the current interval (moving 10 s, stationary 30 s, from server config), or the heading has turned more than 25 degrees, or the bus has moved more than 150 m. Using distanceInterval: 0 is deliberate: it keeps updates arriving while the bus is stationary, so a parked bus keeps sending fresh points and is not mistaken for a lost one. Phones are assumed to be on a vehicle charger.
Platform reality. The 5 s request above is only what the app asks the operating system for. Neither Android nor iOS promises delivery at that rate: battery management, permission changes, force-quitting and iOS background limits can delay, thin or stop updates. The design therefore depends on detection (Stale, Offline, and the permission and health fields) and recovery, never on a promised cadence. Measured behaviour for each platform is recorded under the gates in section 13.4.
9.5 Local queue and uploader
CREATE TABLE points (  id TEXT PRIMARY KEY,                 -- client_point_id (UUID)  trip_id TEXT NOT NULL, recorded_at INTEGER NOT NULL,   -- epoch ms, clock-corrected  lat REAL NOT NULL, lng REAL NOT NULL, accuracy REAL, speed REAL, heading REAL,  state INTEGER NOT NULL DEFAULT 0,    -- 0 pending, 1 in flight  attempts INTEGER NOT NULL DEFAULT 0, next_try_at INTEGER NOT NULL DEFAULT 0);CREATE INDEX points_pending ON points (state, next_try_at, recorded_at);CREATE TABLE outbox (id TEXT PRIMARY KEY, kind TEXT, payload TEXT, created_at INTEGER,                     attempts INTEGER DEFAULT 0, next_try_at INTEGER DEFAULT 0);CREATE TABLE kv (k TEXT PRIMARY KEY, v TEXT);   -- clock offset, active trip, config, start-acked flag
SQLite runs in WAL mode so a crash cannot corrupt the queue.
Flush algorithm
Triggers: a 10 s timer while points are pending, connectivity regained, app returning to the foreground, and trip end.
Gate: do nothing until the trip's start request has been acknowledged by the server (kv.start_acked). Otherwise the server would reject early points as outside the trip window and the app would discard them.
Select up to 200 pending points ordered by recorded_at, mark them in flight, and send one request with the health block.
For each result: accepted or duplicate deletes the row; rejected deletes it and logs the reason; anything not mentioned reverts to pending.
On a network error or 5xx, revert the batch to pending and back off 2 s, 4 s and so on up to 60 s, with 20% jitter. On 401, refresh the token once and retry. On 413, halve the batch size. On 429, wait for Retry-After.
Update the clock offset from server_time and apply any new config and min_app_version.
On app start, reset rows stuck in flight for more than 60 s to pending.
Limits and delivery guarantee. The queue has no point-count cap. A row is about 150 bytes, so 100,000 points is roughly 15 MB, about 11 days of continuous tracking at 10 s. Captured points are never deleted to make room. Two cases can still prevent delivery, and both are counted and reported, never silent:
Older than the server window. The server rejects points recorded more than 24 hours earlier (time_stale), so the app discards queued points older than 24 hours, increments dropped_stale, and logs it. The guarantee in section 1.1 therefore covers outages of up to 24 hours.
Storage exhaustion. If free device storage falls below 200 MB or the queue file passes 100 MB, the app stops capturing new points, shows a red Storage full banner, adds the time paused to capture_paused_s, and sets queue_full in the health block so the dashboard shows a warning. It does not thin or delete what it already holds.
Both counters appear in the health block and the Diagnostics screen, and the pilot report states them.
9.6 Trip controller and recovery
States: Idle, Checking (permissions and consent), Active, Ending, Error.
Start: write trip.start to the outbox with an idempotency key and the corrected start time, begin tracking at once, and mark start_acked when the server confirms. A driver is never blocked from starting by a bad network.
End: stop accepting new points, flush the queue completely, then send trip.end. If the flush cannot finish, the app tells the driver the remaining points will upload in the background and keeps the uploader alive.
Recovery on launch: read the active trip from kv; if online, confirm with GET /driver/active-trip. If the server says the trip ended, stop tracking and flush. If it is still active, make sure the task is running (hasStartedLocationUpdatesAsync) and restart it if not.
Reboot: the MVP does not auto-start tracking after a phone restart. The bus shows Stale then Offline and the dashboard operator phones the driver; opening the app resumes tracking. A boot receiver on Android is a later option.
9.7 Outbox
The outbox sends trip start, trip end, incidents (with a resized photo, 1600 px and JPEG 70%, uploaded by presigned URL first) and consent records. Each entry carries an Idempotency-Key, is retried with the same backoff, and survives restarts. The queue and outbox are processed in order: start, points, end.
9.8 Health, diagnostics and updates
Every upload includes battery, charging state, network type, permission state, queue depth, dropped-stale count, capture-paused time and app version.
A Diagnostics screen shows permission state, whether the tracking task is running, last fix age and accuracy, last successful upload, queue depth, clock offset, app and OS version, and the installation ID. A Share logs button exports the last 500 local events.
If the app version is below min_app_version, a blocking screen sends the driver to the store or the install link.

10.1 Structure
Routes: /login, / (dashboard), /live, /buses, /buses/:id, /drivers, /drivers/:id, /routes, /routes/:id/edit, /trips, /trips/:id, /trips/:id/replay, /alerts, /reports, /users, /audit, /settings.
Server data through TanStack Query (typed client generated from OpenAPI); one 401 triggers a single refresh attempt, then logout.
The UI reads /me capabilities to hide actions a role cannot use. The server remains the only authority.
Every list is server-paginated, filterable and sortable; forms share the Zod schemas with the API.
Standard states everywhere: loading skeletons, empty states with a next action, error boundaries and retry, toasts for results, confirmation for destructive actions.
Performance budget: initial JavaScript under 300 KB gzipped; the map and replay code are loaded on demand.
10.2 Live map implementation
A Zustand store holds busesById, rev, and connection. applySnapshot replaces state; applyBatch and applyStatus ignore any item whose rev is not newer.
MapLibre renders one GeoJSON source of 100 features. Status is shown by colour, icon shape and label together, so it does not depend on colour alone. Clustering is enabled for zoomed-out views.
Updates reach the map at most once per animation frame. Markers glide between positions over about 900 ms on the client; the underlying data is never altered by the animation.
A separate one-second ticker updates the "x s ago" text, so only the side panel re-renders.
Search and filters run in memory (100 buses). Selecting a bus focuses the map and opens its panel with registration, driver, route, trip status, coordinates, speed when reliable, source, and last update.
Banner states: Connected, Reconnecting, Connection lost (with the time of the last update).
The tile style URL and attribution come from configuration so the provider can change without code changes.
10.3 Route editor and replay
Editor: click the map to add stops, drag to reorder, set planned offsets. Validation: at least 2 stops, offsets strictly increasing, no duplicate coordinates. Saving creates a new route version; Build road geometry calls the backend, which uses a RoutingProvider interface and stores the resulting line.
Replay: GET /trips/:id/replay?step=5 returns points bucketed by step seconds (capped at 20,000), plus stop events and alerts for the timeline. The player supports 1x, 4x and 16x speed, a draggable timeline and a marker following the path.

12. Security Implementation
12.1 Tenant isolation in three layers
Code: every repository function takes orgId; an import-restriction lint rule blocks direct table access from other modules.
Routes: a test enumerates the route table and fails if a route lacks a role guard or organization scope.
Database: PostgreSQL row-level security on every organization-owned table, with policies of the form USING (org_id = current_setting('app.org_id', true)::uuid). The application connects as a role that does not own the tables, tables use FORCE ROW LEVEL SECURITY, and each request transaction begins with SELECT set_config('app.org_id', $1, true). Worker jobs set the organization per job. Migrations run as a separate role.
A dedicated test connects with raw SQL under organization A and proves it cannot read, insert or update organization B's rows.
